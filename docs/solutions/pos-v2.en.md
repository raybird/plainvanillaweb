# Multi-Window POS v2: cross-device collaboration and tableside ordering

> **Updated**: 2026-11-27  
> **中文**：[Multi-Window POS v2](./pos-v2.md)  
> **Entry point**: [#/solutions/pos-v2/admin](#/solutions/pos-v2/admin) · **Issue**: #16 · **Decision**: [ADR 0109](../decisions/0109-pos-v2-webrtc-host-authority.md) · **Protocol**: [POS v2 protocol spec](../superpowers/plans/2026-11-26-pos-v2-protocol.md) (Chinese)

The first [Multi-Window POS](./pos.en.md) only coordinates tabs on one computer. v2 lets staff tablets and phones, and customers' own phones, join the same orders from other devices. One tab of the admin page is the **host**, and orders live only in the host's IndexedDB. Other devices complete a handshake through a self-hosted signaling server, then open a WebRTC DataChannel straight to the host and place orders and act on them over RPC. Order and authorization data travel only inside the DataChannel, never through the signaling server.

This is a demo: **no real payments and no personal data**. v1 stays unchanged, and the two do not share data.

## 1. How to use it

You need a computer running the host page (Chrome or Edge), staff devices and customer phones on the same Wi-Fi as the host (STUN only, no TURN), and a self-hosted signaling server (see "Self-hosting the signaling server" below).

| Role | Route | Where it runs |
| --- | --- | --- |
| Host (admin) | `#/solutions/pos-v2/admin` | The shop's computer; one tab per namespace is the host, others are read-only |
| Staff pairing | `#/solutions/pos-v2/join` | Scan the pairing QR code on the host page, or enter the connection code |
| Order, kitchen, display | `#/solutions/pos-v2/order`, `/kitchen`, `/display` | Opened automatically after pairing is approved; reuses the v1 screens |
| Shop entrance | `#/solutions/pos-v2/home` | Customers scan the shop entrance QR code and pick an open table |
| Tableside ordering | `#/solutions/pos-v2/table?t=<table>` | Customers scan the table card, enter the table code, and order |
| Order tracking | `#/solutions/pos-v2/track?o=…&k=…` | Customers scan the order QR code shown after a counter order; it shows only that order |

Remote device URLs carry `room` (the room) and `sig` (the signaling URL). The QR codes generated by the host page include them, so devices need no setup.

A complete run:

1. In the host page's "Signaling server" section, paste the signaling URL (`https://` is turned into `wss://`) and press "Test connection". When the page is opened with `sig=` in the URL, the value is saved only after you confirm.
2. Press "Generate pairing QR code": the staff device scans the pairing QR code (or enters the connection code at `#/solutions/pos-v2/join`); the host approves it and assigns a role (order, kitchen or display; kitchens need a station name).
3. "Tables": opening a table shows a 6-digit table code, once only (after a reload, press "New table code" to see one). "Table card QR codes" can be printed; printing outputs only the cards.
4. Customers scan the table card, enter the table code and order; everyone at the table shares the same code. "My orders" shows the pickup number, progress, and how many orders are ahead.
5. The kitchen claims and finishes the order, the display shows the number, and "Picked up" closes it. After a counter order, the order device shows an order QR code so customers without a table can follow it.
6. "Close table" when the party leaves: the old code and already-joined pages can no longer order into the next dining session.

Reset: "Reset demo data" deletes only the order database and **keeps the room**, so printed table cards and QR code URLs keep working. Credentials and dining sessions also live in the order database, so paired staff devices must pair again and tables must be reopened. "Regenerate room" replaces the room and the host key; every QR code and paired device must be set up again, so it asks for confirmation first. Add `?ns=<name>` for a separate data set.

### Self-hosting the signaling server

The project **does not run a public signaling server**; host one yourself, either way below. While no signaling URL is set, the host page shows these two command sets with copy buttons, and the commands download files of the same version as the page (`v3.4.1`). Only "download, then run" is offered, never `curl | sh`, so you can read the files before running them.

**Option 1: Node + Cloudflare Quick Tunnel** (Node 22+ and [cloudflared](https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/downloads/); no account needed)

```bash
curl -fsSLO https://cdn.jsdelivr.net/gh/raybird/plainvanillaweb@v3.4.1/server/signaling.mjs
node signaling.mjs --tunnel
```

`signaling.mjs` is a single file with no dependencies and runs from an empty folder. `--tunnel` starts a Quick Tunnel and prints the host page link with `sig=`. If cloudflared is missing or no URL shows up, it prints manual steps, and the signaling server keeps running at `http://127.0.0.1:8787`. If port 8787 is already used by another program on this computer, the server prints a hint and exits: add `--port 8788` (or any free port) to the second line and run it again. The Quick Tunnel follows that port, and the other steps stay the same. The Quick Tunnel URL changes on every start: after a restart, update the host page setting and have paired devices scan again: credentials are bound to the signaling used at pairing (joining), so when a URL carries different signaling, a staff device asks whether to switch and a customer phone asks for the table code again.

**Option 2: your own Cloudflare Worker** (a Cloudflare account, the free plan is enough, and Node)

```bash
mkdir pos-v2-signaling && cd pos-v2-signaling
curl -fsSLO https://cdn.jsdelivr.net/gh/raybird/plainvanillaweb@v3.4.1/server/cloudflare/worker.js
curl -fsSLO https://cdn.jsdelivr.net/gh/raybird/plainvanillaweb@v3.4.1/server/cloudflare/wrangler.jsonc
npx wrangler@4 login
npx wrangler@4 deploy
```

The `https://pos-v2-signaling.<account>.workers.dev` printed after deploying is the signaling URL; paste it into the host page. The URL is stable, so this suits longer use. The Worker keeps each room's host binding in a Durable Object (SQLite storage, available on the free plan) and uses the WebSocket Hibernation API.

**Origin allowlist**: the signaling server accepts only allowlisted `Origin`s, by default `https://raybird.github.io`, `http://localhost:*` and `http://127.0.0.1:*`. If you host the front end yourself, add your site: `--allow-origin <origin>` (repeatable) for Node, or `ALLOWED_ORIGINS` in `wrangler.jsonc` for the Worker. Other settings: `--ice-servers`/`ICE_SERVERS` (for example to add TURN), `--port`, `--host`, `--app-url`/`APP_URL`.

## 2. Architecture

```text
 Staff devices (order/kitchen/display)     Customer phones (table/track)
        │  RemotePosSession                     │  RemoteTableSession
        │  PeerLink ─ RPC client                 │
        └──────── DataChannel (orders, authorization) ────────┐
                                                             ▼
  Self-hosted signaling (relays SDP/ICE only) ◀── Host tab: PosV2Host ─ PosV2Hub (auth, RPC, pushes)
   signaling.mjs or Worker                                   │ writes: PosV2Repository (one readwrite transaction)
                                                             ▼
                      IndexedDB  vanilla_solution:<ns>:orders  ← the only authoritative state
                               vanilla_solution:<ns>:room    ← roomId, hostSecret
```

- **One host**: a Web Lock on the admin page guarantees a single host tab per namespace. The signaling server binds the room's host seat trust-on-first-use (the first host that connects with the `hostSecret`; the binding is cleared after 24 hours without a host).
- **Remote devices hold no authoritative state**: even on the host's own computer they go through a DataChannel. Cross-device mutual exclusion comes from IndexedDB transactions running one after another on the host; it is not a distributed lock.
- **Thin signaling**: it only relays handshake messages and stores no orders. Once a direct connection is up, the host or a device losing and regaining signaling does not tear it down; devices rebuild the link right away only when the host is a new instance (the host tab reloaded, so the instance id in `host-online` changed).

## 3. Data flow

Data model (`POS_V2_SCHEMA_VERSION = 1`):

- `orders`: v1 fields plus `principal` (the credential that placed it), `source` (`device`/`table`), `tableId`, `diningSessionId`; a unique compound index on `[principal, requestId]`.
- `tables`, `sessions`: tables and dining sessions. `credentials`: staff device and table credentials, storing only secret hashes. `pairing`: pairing tickets.
- The room (`roomId`, `hostSecret`) lives in a separate database that resetting demo data does not delete.

Authorization:

| Identity | How it is obtained | What it allows |
| --- | --- | --- |
| Staff device | Pairing (a pairing token in the QR code valid for 5 minutes, or a 6-digit connection code; within that time every device that applies must be approved one by one) → the host approves and assigns a role | By role: place orders; claim, finish and take over in the kitchen; mark picked up at the display |
| Customer (joined table) | Table + table code (shared within a dining session; 5 wrong tries trigger a cool-down) | Order into the table's current session; see orders placed with this credential |
| Order tracking | A token the host derives from `hostSecret` for a counter order | See that one order only |

- **Writes**: every write runs in one `readwrite` transaction on the host that re-reads the credential, decides and writes back; an order is refused if the credential was revoked just before.
- **Deduplication**: the key is "credential + `requestId`". Replaying someone else's `requestId` creates your own new order and never returns theirs.
- **Transitions**: same as v1 (claim, ready, takeover, pickup); cancelling a pending order is done only from the order list on the admin host. The host decides whether a remote kitchen station is alive from its connection and heartbeat; takeover is allowed only after it has been offline past the timeout.
- **Pushes**: after a write the host coalesces pushes of `kitchen`, `display`, `order`, `myOrders` and other topics within 100 ms; each device receives only what its credential may see. On a gap in the push sequence the device runs `sync`.
- **Orders ahead**: the number of pending orders in the whole shop with a smaller sequence number.

## 4. Failure modes

| Situation | Expected behavior | How it is verified |
| --- | --- | --- |
| Reload (device) | Credentials are in localStorage; after a reload the device reconnects and authenticates without pairing again or re-entering the table code | Browser tests |
| Reload (host) | Room, credentials and tables come back from IndexedDB; devices see a new host instance id in `host-online` and rebuild the link immediately | Browser test `runPosV2RecoveryTests` |
| Lost between send and reply | The order is saved locally first and shown as "Waiting for the host"; after reconnecting it is resent with the same `requestId`, and an order the host already wrote comes back as the same single order | Browser tests (lost after and before the write), `tests/pos-v2-remote-session.test.js` |
| Late-joining device | After authenticating it gets full data for every subscribed topic | Browser tests |
| Concurrent actions on one order | They run one after another on the host; one succeeds, the other shows that another station handled it | Browser test with two remote kitchens claiming at once |
| Takeover while the station is online | Refused; once it has been offline past the timeout the host pushes again and other stations show "Take over" | Browser tests, `tests/pos-v2-hub.test.js` |
| Credential revoked or room regenerated | The device asks to pair again or re-enter the table code; pending orders under the old credential are not resent with the new one, and each is reported | `tests/pos-v2-hub.test.js`, `tests/pos-v2-remote-session.test.js` |
| Close and reopen a table | Old pages get `SESSION_CLOSED`, the old code gets `CODE_INVALID`, and customers still see their own orders | Browser tests |
| Host tab closed | Devices show "Waiting for the host…" and recover when the host returns | Browser tests `runPosV2HubTests`, `runPosV2RecoveryTests` |
| A second host tab | It cannot get the Web Lock and is read-only | Browser tests |
| Signaling server goes down | Established links no longer use signaling and are unaffected; signaling reconnects with backoff. After the host's signaling reconnects, `host-online` carries the same instance id and devices keep their links | Browser test `runPosV2RecoveryTests` (when the host's or the phone's own signaling reconnects, the link is not rebuilt and the host keeps the phone's connection), `tests/signaling-client.test.js` (backoff), `tests/signaling.test.js` (instance id) |
| Many devices reconnect at once | An authenticated host's signaling rate allowance scales with the number of peers (50 × (1 + peers) messages per 10 s), so answering every handshake does not get it closed with 4008 | `tests/signaling.test.js` |
| The URL's signaling differs from the one used at pairing (joining) | A staff device shows both signaling URLs and asks before sending its credential; a customer phone does not send its table credential and asks for the table code again | Browser test `runPosV2RecoveryTests` |
| Concurrent guesses of a table or connection code, made-up table ids | Requests still being verified count as failures, so even concurrent requests on one connection let at most 5 reach verification; unknown table ids count only against the connection and cannot push out another table's cool-down | `tests/pos-v2-hub.test.js` |
| Oversized pushes, ordering too often | Snapshots are cut at a byte budget and marked `truncated` without closing the connection; one principal may place at most 30 orders a minute, then gets `RATE_LIMITED` (resending an existing `requestId` does not count) | `tests/pos-v2-hub.test.js` |
| Direct connection fails (symmetric NAT, mobile networks) | After a timeout it shows "Cannot connect directly, TURN is needed" with a retry, instead of waiting forever | Browser test `runPosV2HubTests` (relay-only without a TURN server) |
| Malformed messages | Replies `BAD_MESSAGE` when there is an id, drops otherwise, counts both; closes the connection after 20 | `tests/pos-v2-hub.test.js`, browser tests |
| Slow device (backpressure) | Pushes pause while `bufferedAmount` is above 1 MiB; one fresh snapshot is sent once the buffer drains | `tests/pos-v2-hub.test.js` |
| No signaling configured | The host still works locally and shows both self-host command sets; no `console.error` | Browser smoke test |
| No WebRTC or WebSocket support | Shows an explanation and does not start | `remoteSupported()` |

## 5. Resources and cleanup

- Host tab: IndexedDB connections, the host Web Lock, the signaling WebSocket, one RTCPeerConnection per device, heartbeat and presence timers, a `beforeprint` listener. When a device's DataChannel closes or its heartbeat times out, the host releases that device's RTCPeerConnection right away; everything is released when leaving the route (`disconnectedCallback`).
- Remote device: the signaling WebSocket, one RTCPeerConnection, RPC timers; released when leaving the route.
- Reset demo data: deletes `vanilla_solution:<ns>:orders` and keeps `vanilla_solution:<ns>:room`.
- localStorage on devices: the signaling URL (host), `credential:<roomId>` (staff credential), `table:<roomId>` (table credential), `watches:<roomId>` (order tracking, up to 50), `pending:<roomId>` (orders awaiting confirmation), all prefixed with `vanilla_solution:<ns>:`.

## 6. Gaps before production

- **Authorization and identity**: the trust model is in [ADR 0109](../decisions/0109-pos-v2-webrtc-host-authority.md). The host seat is bound trust-on-first-use with no account system; table and connection codes are 6 digits, with cool-downs to limit guessing. A real system needs shop accounts, device management and audit logs.
- **Transactions and payment**: no payment, invoices, refunds or reconciliation.
- **Cross-device sync and backend**: the host tab is the only authority, so ordering stops when the host computer is off; there is no failover or off-site backup. Only STUN is used; mobile networks or symmetric NAT need your own TURN (`--ice-servers`/`ICE_SERVERS`).
- **Personal data and auditing**: no customer data is collected; orders live only in the host browser.
- **Other**: up to 64 devices per room. The Quick Tunnel URL changes every time, so use your own Worker for longer use. Browsers may clear data when storage runs low; a real system needs `navigator.storage.persist()` and backups.
